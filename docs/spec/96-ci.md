# CI 接法

lab 自己的持续集成：跑在哪、跑什么、怎么读结果、哪些不许进。

**测什么、测到什么程度、哪些不测**由 [#29](https://github.com/trytoreachpeak0/8005-test-lab/issues/29)
定，见 [95-self-test.md](95-self-test.md)。本文只定那些东西怎么被自动跑起来。

**产物怎么留**不在本文：证据的检索与保留归
[#25](https://github.com/trytoreachpeak0/8005-test-lab/issues/25)，Observation 的归
[#26](https://github.com/trytoreachpeak0/8005-test-lab/issues/26)。

## 1. `.github/` 属于哪一类

工作区 `CLAUDE.md` 把 lab 仓的东西分两类：产品代码等地图清空，不是代码的东西（规格、清单、
`.gitignore`）现在就落。仓库 `CLAUDE.md` 把第一类点名成 `src/`、`tests/`、`adapters/`、`lab.ps1`。
**`.github/` 两张清单里都没有。**

**它是第三类，判据是：不是代码的东西现在就落，除非它落地之后会自己动起来。**

`.gitignore`、`CONTEXT.md`、`docs/spec/` 落进仓库之后什么都不做，读它们的人自己决定何时用。
一个 workflow 文件落进去之后会被 GitHub 真的调度、真的去调 `lab.ps1`——而 `lab.ps1` 今天不存在，
所以那是**每次 push 一次红**。

永久红的代价不是难看：**红色饱和之后，真的红也不出声了。** 这是 #29 那条判据（「坏掉的时候会不会
不出声」）的镜像形式，同 #6 对真车 CPE 切 AP 的判断——「那种红是噪音，会训练人忽略红色，比没有
红色更糟」。

**定：**

| 东西 | 什么时候落 |
| --- | --- |
| 本文 | 现在 |
| `.github/workflows/*.yml` | 跟 `lab.ps1` 的第一个可运行版本一起 |
| 两个 runner 的注册 | 同上 |

runner 注册**可以**提前做（一个没有 workflow 的 runner 只是空转监听，不会自己动起来），但没有理由
提前——提前只会让工作区 `CLAUDE.md` 那张 runner 表提前失真，而那张表自己记着「它漏记了两个 runner
至少一天，而这张表是判断『某个仓有没有 CI』的唯一依据」。

## 2. runner：两个，装在 `vm01` 上

`trytoreachpeak0` 是个人账号不是组织，**一个 runner 只能绑一个仓库**（工作区 `CLAUDE.md`）。所以
lab 要 CI 就必须新装，不能借。

2026-09-09 实读 `gh api repos/<仓>/actions/runners`：五个 runner 全部 online，`8005-test-lab`
**一个都没有**，仓库是 private（挂 self-hosted runner 的仓绝不能是 public——工作区 `CLAUDE.md`
三条硬约束的第一条，已满足）。

| runner | 模式 | 账户 | 标签 |
| --- | --- | --- | --- |
| `win11-01-test-lab` | 服务（session 0） | `NT AUTHORITY\NETWORK SERVICE` | `pwsh7` `headless` |
| `win11-01-test-lab-desktop` | 交互式（session 1，登录触发的计划任务） | **`agvops` + `RunLevel=Highest`** | `pwsh7` `interactive-desktop` |

两个都带 `self-hosted` `Windows` `X64` `win11-01`。

### 2.1 标签取什么，不取什么

- **不打 `dotnet8`。** #16 定死「整个仓库没有 .NET 工程，也不打算有」。打上它就是声明一个用不着的
  能力，而那张 runner 表是判断「某个仓有没有 CI」的唯一依据。
- **不打 `golden-renderer`。** 工作区 `CLAUDE.md`：「只给需要金机的 runner 打 `golden-renderer`
  标签，别的 runner 不要带」。95-self-test.md 4.2 明写 lab 的 WPF 夹具**不要求黄金渲染机那七条
  环境条件**（分辨率 / DPI / 主题 / 字体 / locale / 时区 / 渲染模式）——它不产像素基线。
- **新标签两个**：`pwsh7`（三台机器都有 pwsh 7.6.5，但今天没有任何 runner 声明它）与
  `interactive-desktop`。

### 2.2 标签必须映射 `registry.json` 里已有的词，不新造

#5 的决议里，`vm01` 那一行声明的是 `hasInteractiveDesktop: true` 与 tags `ci-runner`、
`golden-renderer`（`registry.json` 本身还没落地，#5 的决议评论是权威）。

**runner 标签是那些字段的 runner 侧投影，用同一套词汇**——`interactive-desktop` 对应
`hasInteractiveDesktop`，不叫 `interactive`、不叫 `desktop`、不叫 `wpf`。

理由是 #29 那条判据：两套词汇分叉是**静默的**。一个 job 因为标签与登记册的说法对不上而永远排不上
队，表现是「CI 没触发」，而不是一条错误。

这条也是第 5 节那个接缝的一半：**标签选的是「什么样的机器」，不是「哪一台机器」。** 工作区
`CLAUDE.md` 已经定过同一条（「`runs-on` 一定要带 `headless` 或 `golden-renderer`」），#5 定的
「登记册只声明能力、从不出现角色名」是它在另一侧的同一句话。

### 2.3 交互式 runner 必须以 `agvops` 且提权跑

不是风格，是桌面互斥体拿不拿得到的问题。见第 4 节。

## 3. 四个 job

| job | runner | 跑什么 | concurrency | `timeout-minutes` |
| --- | --- | --- | --- | --- |
| `unit` | `headless` | `tests/unit` | `${{ github.workflow }}-${{ github.ref }}` | 15 |
| `machine-headless` | `headless` | `tests/machine` 里 `Requires` 不含 `interactiveDesktop` 的 | 同上 | 30 |
| `machine-desktop` | `interactive-desktop` | `tests/machine` 里 `Requires` 含 `interactiveDesktop` 的，加真装置那两条场景（7.2 节） | **`win11-01`** | **60** |
| `scenario` | `headless` | `lab scenario list` 列出的、rig 不需要交互式桌面的那些 | **`win11-01`** | 30 |

`machine-desktop` 的 60 分钟是「最坏 30 分钟排桌面锁 + 30 分钟跑」，与那张图给 mes-ingest 的新
预算一致。**GitHub 的 `concurrency` 等待不算进 `timeout-minutes`**（它从 job 开始执行才计时），
所以那 60 分钟里只有桌面互斥体的排队，不含同仓 job 之间的排队。

`scenario` 的 30 分钟对着实测来：今天 `l2.yml` 跑八条合成场景是 6–10 分钟（见 7.2 节），
`l2.yml` 自己给的是 20。留一倍余量，因为 lab 这边多了跨机的传输。

**两个 job 用 `group: win11-01` 而不是 workflow 名。** 理由不是桌面（跨仓的桌面由互斥体管，
`concurrency` 只在单个仓库内生效），是**那台客户机 20 vCPU / 8 GB 已经超订**——`8005-mes-ingest`
正是为此把它的组从 `desktop` 改成 `win11-01`，注释写着「a WPF test that waits on a window does not
hold its timing there」。

**跑哪些测试由声明派生，CI 不写清单**（#29）：每个 `tests/machine/` 测试的 `$LabTestFootprint`，
它的 `Requires` 同时是足迹（#31）与选择器。**CI 只需要说清「这台机器有什么」**，那就是 runner 标签。
做法取自 `Get-WpfDesktopTestFilter.ps1` 那条教训——手写清单头一版就漏了两个类。

**场景清单同理来自 `lab scenario list`**（#10），不是 workflow 里的手写数组。

### 3.1 为什么 CI 要跑场景，不只是跑 `tests/`

按 #29 那条判据：**这段代码坏掉的时候会不会不出声。**

`Lab.Core` 的编排那条路——绑定校验、传输建立、钩子调用顺序、证据封存——坏掉时 `tests/unit` **一条
都不会红**：按 #16 的模块分界，`tests/unit` 根本不加载 `Lab.Core`。**唯一能让编排出声的是真的跑
一条场景。**

那条路今天在 `8005-agv-control-server` 的 `l2.yml` 里每次 push 都被跑（八条合成场景，合计约两
分钟）。#17 定它们会逐条迁进 lab，**而一条场景切走的那一刻，它的自动回归也跟着走**——如果 lab 这
边没有 job 接住，那八条就从「每次 push 都验」变成「有人想起来才跑」，而这个退化是不出声的。

**「CI 里要构建被测系统」不是额外代价。** #12 定构建源是 origin 上的一个 commit、缓存键是
`<角色>-<commit>-<flavor>` 加 `publish.ok` 戳文件——lab 仓的一次 push 不改 control-server 的
commit，所以除第一次外全是缓存命中。那是 lab 跑任何一条场景时本来就要做的事，不是 CI 特有的负担。

## 4. 桌面互斥体：lab 是第三条取锁的代码路径

`Global\W2G-InteractiveDesktop`，唯一定义处是 `repos/8005-mes-ingest/Invoke-WithDesktopLock.ps1`。
名字是契约、代码不是；lab 自己拷一份获取逻辑，不建共享包（#6 定，工作区 `CLAUDE.md` 同）。

**「第五个持锁者」那个数错了**（#6 与 #29 的评论里各有一处）。那是从「`vm01` 上五个
`Runner.Listener` 进程」推来的，而 runner 不是持锁者。2026-09-09 实测 `main` 上取这把锁的代码路径
是**两条**，都在 `8005-mes-ingest` 里：

| 取锁点 | 怎么取 |
| --- | --- |
| `Invoke-WithDesktopLock.ps1:72` | `desktop-tests.yml:80` 用 `-Command { }` 包住一段命令 |
| `Invoke-WatchUiTests.ps1:169-170` | 自己 `new Mutex`，名字经 `-NameOnly` 取自上面那个文件 |

筛法：`grep -rn --exclude-dir=.git --exclude-dir=bin --exclude-dir=obj -e "Threading.Mutex"` 与
`-e "Invoke-WithDesktopLock"` 两个口径，排除 `.scratch/` 与 worktree 目录。**lab 是第三条。**

（`8005-agv-control-server` 的 `scripts/DesktopLock.psm1` 会是第四条——据 `8005-agv-program` 那张图
票 01 的决议它已经写好，但它活在 `fp/v2-impl` 分支上，本工作区的 `main` 克隆里两个口径都零命中。
见第 4.3 节。）

### 4.1 lab 拷的是哪一份形状：Enter/Exit 抛异常，不是包装器 + `exit`

两份先例形状不同，lab 取后一份：

| 先例 | 形状 | 它的调用方 |
| --- | --- | --- |
| `Invoke-WithDesktopLock.ps1` | `-Command { }` 包住，退出码原样传出 | workflow step |
| `scripts/DesktopLock.psm1`（control-server） | `Enter-DesktopLock` / `Exit-DesktopLock`，**抛异常** | 长脚本内部要占桌面的那一段 |

理由原样适用：**`exit` 会跳过 `finally` 里的进程清理与证据落盘**，而 lab 的编排器正是那种长脚本
——它必须在 `finally` 里封存证据（#11）。异常走 `catch`，编排器照常写 FAIL 证据。

取锁点**尽量靠后**（第一个 WPF 进程启动之前，不是脚本开头），释放在 `finally` **最后一行**（对端
进程停掉之后）。排队期间不该占着任何东西；早放会把桌面交给另一个仓，而这边的窗口还在关。

### 4.2 超时 1800 秒，超时之后的结局是码 4

- **超时值 1800 秒。** 实测单次持锁上界约 8 分钟（`watch-window-visual` 一次迭代约 7.3 分钟、
  `desktop-tests` 那 163 个测试几分钟、L2 真装置场景约 25 秒）。30 分钟是三倍余量，**同时仍是有限
  值**——真出异常时以「谁占着」说明原因，比挂到 job 的 `timeout-minutes` 上只留一行「已超过最大
  执行时间」强。无限等待被否掉就是这一条：诊断信息会消失。
- **超时之后 lab 的结局是 `notAttempted` / 退出码 4，不是那份先例的 `exit 3`。** #33 已经把这一刀
  定过了——[80-cli.md](80-cli.md) 明写「**4 是 `Invoke-WithDesktopLock.ps1:93` 那条 `exit 3`
  （`WATCH_UI_SERIALIZATION_BUSY`）的推广**」。它不是失败，是没跑成。
- **`machine-desktop` job 的 `timeout-minutes` 给 60**（最坏 30 分钟排队 + 30 分钟跑）。

### 4.3 #6 那条「默认值留 0」的前提没了

#6 定过：「`TimeoutSeconds` 的默认值留在 0 不动，只让 lab 传一个真的超时。」

那条的前提是**lab 会是第二个持有方**。前提在 2026-09-08 消失了：`8005-agv-program` 那张图的票 01
把 `8005-agv-control-server` 接上了同一把锁（`scripts/DesktopLock.psm1`，四个会起 WPF 的入口），
并把 `Invoke-WithDesktopLock.ps1` 的默认超时从 0 改成 1800。它的验收是三层（各仓自检 6 条断言、
跨仓双向互等 7.9 秒、mes-ingest 持锁时 L2 真装置场景排队后 PASS）。

**那批改动落在 worktree `8005-fp/` 的 `fp/v2-impl` 与 `fp/batch-2` 分支上，2026-09-09 尚未合进
`main`**——本工作区的克隆读到的仍是 `[int]$TimeoutSeconds = 0`（`Invoke-WithDesktopLock.ps1:56`）。

**对 lab 没有影响，两种情况下做法相同：lab 自己传一个非零超时。** 默认值是 0 还是 1800，只决定
mes-ingest 自己的作业会不会因为撞上别的仓而变红，那是那张图的事。**本文不依赖那批改动是否合并。**

### 4.4 跨账户 ACL：实测出来了，不用再猜

`Invoke-WithDesktopLock.ps1:45-48` 记着一条「已知边界」：跨账户还没打通，「哪天有个服务账户
（session 0）的作业也要持这把锁，就需要给互斥体显式设一个允许两个账户的 `MutexSecurity`……**到那时
再加，不要提前猜 ACL 该长什么样**」。

**不用猜了。** 2026-09-09 实测（控制端，pwsh 7）：一个命名内核互斥体的默认 DACL 是

```
D:(A;;0x1f0001;;;SY)(A;;0x1f0001;;;BA)(A;;0x120001;;;S-1-5-5-0-<logon session>)
```

即 `NT AUTHORITY\SYSTEM` 全权 + **`BUILTIN\Administrators` 全权** + **创建者那一次登录会话**
（不是那个账户）的 Modify / ReadPermissions / Synchronize。

`NT AUTHORITY\NETWORK SERVICE`——四个服务模式 runner 的身份（45-footprint.md 实测）——**不在里面，
也不是 Administrators 成员**。所以：

- **`agvops` + `RunLevel=Highest` 建的锁，一个 headless runner 上的 job 打不开**，会在
  `[Threading.Mutex]::new()` 上吃 `UnauthorizedAccessException`。而 `Invoke-WithDesktopLock.ps1:72`
  没有 catch 它、`$ErrorActionPreference = 'Stop'`——那是**脚本崩掉，不是「锁忙」**。
- **反过来能开**：NETWORK SERVICE 先建的锁，DACL 里有 Administrators 全权，`agvops`（本机
  Administrators 成员，提权后 token 里那个组是 enabled）打得开。
- **所以失败是间歇的**：谁先建决定 DACL，而那取决于当天哪个 job 先跑。**一个只在特定顺序下才炸的
  失败。**

**lab 侧的做法是让它不发生，不是修它**：所有取这把锁的 lab job 都跑在 `interactive-desktop`
runner 上（`agvops` + `RunLevel=Highest`，照 `win11-01-mes-ingest-desktop` 的做法），跨账户就不
出现。这也是第 2.3 节那条约束的全部理由。

#6 那条「互斥体创建时显式设允许两个账户的 `MutexSecurity`」**仍然要做，但理由是真车**——真车上
ssh 登录的是 `agvops`、桌面用户是 `HT`，那是 run 作用域的事，不是 CI 的。**CI 这一侧不需要它。**

## 5. 跨仓：正文那件事不需要发生

票正文第一条是「`8005-agv-control-server` 的 `l2.yml` 改成跨仓 checkout lab：runner 不能走 HTTPS，
只能 ssh」。**两层都不成立。**

### 5.1 方式不是 ssh

工作区 `CLAUDE.md` 的 "Lab VMs" 一节自 2026-09-08 起明写：**全工作区 git 一律 HTTPS**——八个克隆、
工作区仓库、`gh` 的 `git_protocol` 与每一个 `actions/checkout`，三台机器上都没有 `url.*.insteadOf`
改写。「an SSH checkout would need a deploy key per repository, and it buys nothing now.」

那一段自己记着这条结论是怎么翻过来的：票创建那几天的测量是真的（`github.com:443` 从两台机器都不
可达），**结论是错的**——真正坏的是 `AgvAmhs` 把 factory-server 的 WinNAT 临时端口耗尽了
（10330 条不关闭的 AMQP 连接，占掉 16384 个临时端口的 64%）。停掉那个服务，两台机器同一瞬间直连
可达。

**形状先例现成，就在同一个仓的隔壁文件里**：`release.yml:70-78` 已经在跨仓 checkout 一个只读仓
——`actions/checkout@v7` 加 `repository:` 加 `token: ${{ secrets.ONBOARD_HMI_TOKEN }}` 加 `path:`，
注释写明「the default GITHUB_TOKEN is scoped to this one and cannot see it」。

它还带着一条纪律，比 checkout 本身值钱（第 88-90 行）：**「it is handed the local mirror rather
than the GitHub URL so that no token ever reaches a git command line or a global git config on a
runner that outlives this job」**——self-hosted runner 是长命的，凭据不能落在它身上。

### 5.2 更重要的是那件事本身不需要发生

#17 定**逐条切、切一条删一条、不双跑**。所以任一时刻：

- 还没切走的场景完整地住在 `8005-agv-control-server` 里，`l2.yml` 跑它们**不需要 lab**；
- 已经切走的完整地住在 lab 里，lab 的 `scenario` job 跑它们**不需要 `scripts/l2/`**。

**没有哪一刻有一个 job 同时需要两个仓的场景代码。** 而 #17 还定了第一条切的是
`real-onboard-normal-load`，它本来就不进 CI——**迁移的头几步 CI 一格都不用动**。

### 5.3 唯一真正需要跨仓读的东西：迁移期的清单对账

#17 定了「手写数组与 `scripts/l2/scenarios/` 目录的差值只能减不能增」。那守的是**旧家不再跑**。

**新家开始跑没人守，而它是不出声的**：一条场景切进 `adapters/wire-to-gate/scenarios/` 却没被
`lab scenario list` 认出来（文件名写错、`.scenario.psd1` 缺失、`psd1` 里的名字与文件名不一致），
表现就是它安静地不存在。#10 定 lab 侧的清单由声明派生，那让 lab 内部自动；**跨仓那条缝没人守**
——control-server 的数组减一行、lab 的目录加一个文件，是两个仓的两次提交。

按 #24 的「不腐烂」三档：跨仓做不到第一档（一个地方 + 两个调用点）；**能做到第二档——把两份读回来
比对**。

**定**：lab 的 CI 加一步 `migration-drift`，`fetch-depth: 1` 加 `sparse-checkout` 只取
`scripts/l2/scenarios/` 与 `.github/workflows/l2.yml`（`evidence/l2/` 占那个仓 2626 / 3720 = 71%
的文件数，#17 实测；体积不是问题，文件数在 checkout 时间上是），把三份列表读回来比：

1. `l2.yml` 的手写数组；
2. `scripts/l2/scenarios/*.ps1`；
3. `lab scenario list`。

判据：**并集等于迁移账（[25-l2-migration.md](25-l2-migration.md)）里那张表的行数，且每一条恰好
出现在一侧。**

**读不回来也算失败**（#24 第 2 条）：sparse-checkout 空了、PAT 过期了、目录改名了——那意味着守卫
瞎了，该修守卫而不是删掉它。「静默通过」是这一步唯一不许有的结局。

**它的保质期就是迁移期。** `scripts/l2/` 删掉的那次提交里，这一步跟着删。这句话写进步骤的注释。

## 6. 生产车在 CI 上永远够不着，而理由不是 key

网络上够得着：`vm01` 过 NAT 能到 `172.19.162.0/24`（工作区 `CLAUDE.md` 的 A/B 表里「客户机 →

在生产车上跑」，不是「由 CI 跑」。人或 agent 手动发起时它照跑，`Grant` 也在那时才有人给。

## 8. 怎么读结果

### 8.1 退出码

#33 定，[80-cli.md](80-cli.md) 是权威。CI 侧照抄：

| 码 | CI 该怎么做 |
| --- | --- |
| 0 | 绿 |
| 1 | 红。**这是 lab 崩在它自己的错误处理之前**——#33 把 1 保留不用，正是为了让这条信息免费拿到（pwsh 里未捕获的 `throw` 与语法错误都退 1，而 `Write-Error` 退 0） |
| 2 | 红（判定失败） |
| 3 | 红（工具自己出错） |
| 4 | **不算红，但绝不算绿** |

**码 4 的显示**：一行 `::warning` annotation 加一段 `$GITHUB_STEP_SUMMARY`（先例
`golden-renderer.yml:202` 那句 `Tee-Object -FilePath $env:GITHUB_STEP_SUMMARY -Append`），内容取
`coverage-attempted.json` 里够不着的那一格。**step 不因为码 4 而失败，job 也不。**

今天 `agv02` / `agv03` 就够不着，而按第 6 节，CI 上三台车全部落在这一格。

### 8.2 重试要解析 JSON，不能只看退出码

「能不能重跑」不上退出码，挂在 `reasonCode` 的 `retryDisposition` 上（`NEVER` /
`AFTER_STATE_CHANGE` / `AFTER_RECONNECT` / `MANUAL_REVIEW`，#33 定）。#10 那条「`ERROR` 可重跑但带
`remoteStateIndeterminate` 的不行」因此是一次查表。

理由是同一条判据：重试这一刀分错了是**响的**（CI 重试了一个不该重的，下一次运行当场暴露），而
「没跑成」这一刀分错了是**不出声的**。

### 8.3 回放永远退 0，所以不能靠退出码判断它

`lab invariant replay` 产 Evidence，`replayVerdict: miss` 是一个**发现**不是一个失败（#29：回放
不进 `tests/`，它是交付物）。**要解析 stdout 那一行 JSON 的 `replayVerdict`。**

形状照 `golden-renderer.yml` 把 `watch-vm-tests` 与像素比较分成两件事的做法：它绿了不能记进「测试
通过」那一栏。

## 9. 从 `l2.yml` 原样带进来的两条纪律

### 9.1 `cancel-in-progress: false`

取消一个跑在 self-hosted runner 上的 job 会把 runner 的 broker 长轮询一起取消，退避重试耗尽后会话
卡死且不自愈。**2026-09-03 实测空转 4 小时 14 分**，恢复只因为 GitHub 推了一个
`RunnerRefreshConfigMessage`。省下 2 分钟，代价 4 小时。取消一个 **QUEUED** 的 job 是安全的，
照旧发生。

**实测（2026-09-09）：工作区里一共 10 个 workflow 文件，10 个全部带 `cancel-in-progress: false`，
无一例外**（`ls repos/*/.github/workflows/*.yml | wc -l` 得 10，
`grep -rln "cancel-in-progress: false"` 得同样的 10 个文件）。lab 抄第十一份。

**而这一份不适用 #24 那三条「不腐烂」的任何一条**——它记的是一次历史测量（2026-09-03 那 4 小时
14 分），不是一个会变的状态，所以它不会过期。**抄就是对的**，不必为它加守卫，也不必标保质期。

### 9.2 「Exit code is the contract」

runner 的客户机是 zh-CN，`dotnet test` 打印的是「已通过!」不是「Passed!」。**workflow 里任何一步
都不许匹配英文控制台文本。**

这条对 lab 尤其硬，因为 #33 定了 lab 自己的 stdout 是 JSON：**判定读退出码，或读那一行 JSON，
永远不读人话。** `src/` 下不出现裸的 `Write-Host` 是同一条纪律在另一侧（#33）。

## 10. CI 不需要 lab 的任何凭据

- `courier-check` / `vigil-check` 不进 CI → **不需要 webhook key**（那是凭据不是配置，#28）；
- 生产车不点名 → **不需要车的 ssh key**；
- 跨仓只读一个目录列表 → 只需要一把对 `8005-agv-control-server` **只读**的 PAT，**只在
  `migration-drift` 那一步存在，迁移结束跟着删**。

#28 定「能对外发消息的凭据不下车」。**本文是它的镜像：能改被测系统的凭据不进 CI。**

`vm01` 上 lab 的足迹（含 courier 配置副本的 ACL 那条）归 #31，见
[45-footprint.md](45-footprint.md) 第 7 节——那里已经写明它挡不住提权的 desktop runner，而 lab 的
第二个 runner 正是又一个提权的 desktop runner。**位置不在 `C:\actions-runner` 之下，也不在任何
runner 的 `_work` 之下**这条因此更承重了一格。

## 11. CI 是 lab 的第二类调用方，但它不是 agent

地图 Notes 定死「用户只有 agent」。CONTEXT.md 的 Agent 词条：「驱动 lab 的 AI 一方，例如一个
Claude Code 会话。」**CI 不是 agent**——它不判断、不改主意、不读 `SUMMARY.md`。

**这不是本文新造的分类，#33 已经承认过它**：80-cli.md 那张退出码表的第三列标题就叫「CI 该怎么读」。

**所以不加词条。** 不造 `Pipeline`、不造 `CI` 词条、不给 Verb 或 Run 加「触发者」维度。
